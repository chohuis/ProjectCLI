# 공통 계약

상태: 계약 관리 원칙 합의. 구체 API·타입·파일 스키마는 아직 미정이다.

## 계약의 범위

| 항목 | 명시할 내용 |
| --- | --- |
| 호출 | 이름, 인자 수·타입·의미, 필수·선택 여부 |
| 반환 | 결과 타입, 성공·실패, 조회 정보와 사건 |
| 동작 | 상태 변경, 시간 경과, 실행 순서, 동기·비동기 조건 |
| 오류 | 요청 거부·실행 실패·예외의 구분과 호출자 대응 |
| 데이터 | 공용 객체·ID·참조, 직렬화와 파일 형식, 버전·호환성 |

인자 수를 유지해도 의미·단위·기본값·실패 동작을 바꾸면 계약 변경이다. 요청 객체에 필드를 추가하는 경우도 관련 영역에 영향을 주면 승인 대상이다.

## 단일 기준과 변경 승인

- 구현된 호출 형식과 타입은 공용 코드, 동작 의미·승인 상태는 계약 명세를 함께 기준으로 한다.
- 총괄이 계약별 관리 책임자를 지정하고 공용 기준을 관리한다. 구현 담당은 계약을 소비하며 변경안을 제안할 수 있다.
- 변경 요청에는 현재 계약·이유·변경안·영향 영역·검증 방법을 적고 작업 ID와 연결한다.
- 총괄 승인 → 계약·코드 갱신 계획 기록 → 관련 담당에게 기준 전달 → 구현 → QA → 통합 순서를 따른다.
- 승인 기록과 갱신 계약이 전달되기 전에는 기존 계약을 유지한다. 담당자가 다른 영역을 임의로 함께 고치지 않는다.
- 작업에는 적용할 계약 버전과 기준 커밋을 명시한다. 아직 없는 API를 이미 동결된 계약처럼 취급하지 않는다.

## 계약 기록 형식

계약 ID·상태·관리 책임·버전·관련 코드 위치·입력·출력·변경 효과·오류·기대 결과 예시·검증 방법·변경 승인 기록을 적는다. 실제로 필요한 계약부터 작성한다.

## 현재 등록 상태

등록된 구체 계약은 없다. 다음 항목을 기반 구현 전에 명세할 필요가 있다.

| 영역 간 경계 | 정할 내용 |
| --- | --- |
| 표현 ↔ 실행 관리 | 요청 분류, 입력 오류, 결과 표시용 데이터 |
| 실행 관리 ↔ 엔진 | 행동·조회·시간 진행, 변경 확정, 실패 시 상태 |
| 실행 관리 ↔ 저장 | 상태 복사·복원, 실패 결과, 상태 교체 시점 |
| 관리 도구·파일 관리 ↔ 변환 | `.dat` 구조·키 식별·인증·버전·데이터 검증 |

저장할 구체 게임 정보와 시간 진행 단위는 기획 명세에 의존한다. 해당 정보가 미정이면 임의의 최종 API로 확정하지 않는다.
