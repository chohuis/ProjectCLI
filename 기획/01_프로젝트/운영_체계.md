# 운영 체계

이 문서는 역할별 책임, 작업 배정, 협의와 승인, 기록 관리 기준을 정의한다. 게임의 세부 규칙이나 아직 정하지 않은 API를 확정하지 않는다.

## 1. 운영 구조

- 사용자와 메인 채팅을 프로젝트의 기본 협의 창구로 사용한다.
- 메인 에이전트가 총괄을 맡고, 기획은 별도 담당 에이전트로 운영한다.
- 총괄이 필요한 작업에 하위 에이전트를 배정하고 결과를 수집·검토·통합한다.
- 역할은 논리적인 책임 구분이다. 모든 역할을 항상 동시에 실행하거나 같은 에이전트를 영구 유지할 필요는 없다.
- 동시 활동 수는 실제 도구 환경의 한도에 맞춘다. 구현과 QA를 순차 배정할 수 있으며, 특정 동시 실행 수를 프로젝트의 영구 규칙으로 고정하지 않는다.
- 담당 에이전트가 바뀌어도 저장소의 승인된 문서와 작업 기록을 읽고 업무를 이어간다.

## 2. 여섯 역할의 책임

| 역할 | 담당 책임 | 작성·보고 범위 |
| --- | --- | --- |
| 총괄 | 구조와 기술 계약 관리, 작업 분해·배정, 변경 승인, 일정 조정, 통합과 최종 보고 | 개발·운영 기준, 공통 계약, 작업 현황, 기술 결정 기록 |
| 기획 | 요구사항 정리, 동작 시나리오, 완료 조건, 미결정 사항과 기획 영향 분석 | 승인된 요구·동작 명세, 기획 변경안, 검증 가능한 기대 결과 |
| 엔진 구현 | 게임 상태, 요청 검증, 시뮬레이션 처리와 관련 테스트 | 담당 코드·테스트, 계약 관련 영향, 자체 검증 결과 |
| CLI 구현 | 입력·출력과 게임 진행 흐름 연결, 이후 Godot 표현 계층 구현 | 담당 코드·테스트, 사용 흐름과 연결 결과 |
| 데이터·도구 구현 | 데이터 형식, 암호화, 저장·복원, 콘텐츠 관리 도구 | 담당 코드·테스트, 파일·스키마 영향, 복구 검증 결과 |
| QA | 명세 준수, 오류 재현, 기능 연결·회귀·통합 검증 | 작업별 검증 결과, QA 이슈, 미검증 항목 |

각 구현 담당은 자체 테스트와 검증을 수행한다. QA는 이를 근거로 독립적으로 검증하며, 테스트 책임을 QA에만 넘기지 않는다.

## 3. 결정과 승인 권한

| 판단 대상 | 결정 책임 |
| --- | --- |
| 미합의 제품 방향, 게임 규칙·경험, 범위와 우선순위의 중요한 변경 | 사용자 |
| 기존 세이브 지원 중단 등 사용자에게 약속한 지원 정책의 변경 | 사용자 |
| 기존 합의를 유지하는 기술 구조·의존성·일정 조정·인터페이스 변경 | 총괄 |
| 승인된 방향 안의 명세 정리와 기획 해석안 | 기획이 작성하고 총괄이 작업 기준으로 확인 |
| 공통 계약을 유지하는 담당 영역 내부 구현과 버그 수정 | 배정된 구현 담당 |
| 검증 기준에 따른 통과·실패 판정 | QA |
| 통합 완료와 작업 종료 판정 | 총괄 |

- 총괄은 미합의 제품 결정을 기획·기술 결정으로 대신 확정하지 않는다. 기획이 쟁점과 기대 동작을 정리하고, 총괄이 기술 대안·영향을 붙여 사용자에게 전달한다.
- 총괄만 작업을 재배정하고 하위 에이전트를 추가 배정한다. 담당자는 필요성을 제안할 수 있으나 다른 역할의 업무를 임의로 맡거나 새 담당자를 만들지 않는다.
- 승인 대기나 응답 부재는 승인이 아니다. 대기 중에는 기존 계약으로 가능한 작업을 진행하고 의존 작업의 보류 이유를 보고한다.
- 위 승인 절차는 프로젝트 운영 규칙이다. 도구의 실제 파일·네트워크 권한과 승인 정책은 별도로 적용된다.

## 4. 기록의 단일 기준

| 기록 | 기준 위치 | 관리 책임 |
| --- | --- | --- |
| 모든 AI가 읽을 핵심 지침 | [AGENTS.md](../../AGENTS.md) | 총괄 |
| 코드·주석·테스트·변경 기록 규칙 | [개발 규칙](개발_규칙.md) | 총괄 |
| 역할·협의·승인 절차 | 이 문서 | 총괄, 기획은 변경안 제안 |
| 작업 담당·상태·결정·결과 링크 | [작업 현황](작업_현황.md) | 총괄 |
| 게임 요구와 기대 동작 | [게임 설계](../02_게임_설계/)의 해당 명세 | 기획 |
| 영역 간 기술 계약 | [공통 계약](../03_기술_설계/공통_계약.md) | 총괄 |
| 환경의 검증 결과 | [환경 검증](../04_검증/환경_검증.md) | QA, 총괄이 반영 조율 |
| 기능·변경의 검증 결과 | 향후 필요한 작업별 QA 기록과 작업 현황의 링크 | QA |
| 중요한 변경의 사유와 영향 | [결정 기록](../90_결정_기록/) | 총괄, 관련 담당이 근거 제공 |

- 역할마다 같은 내용을 복사한 별도 일지를 만들지 않는다. 요구는 명세, 기술 약속은 공통 계약, 진행 상황은 작업 현황을 기준으로 삼는다.
- 다른 기록에서는 해당 문서·항목·계약 버전을 링크한다. 간단한 작업은 현황의 결과 요약으로 충분하며, 상세 설명이 필요할 때만 별도 기록을 연결한다.
- 현재 설계는 승인된 최신 기준을 설명한다. 중요한 변경 이유는 결정 기록에 남기고, 대체된 결정에는 후속 기록을 연결한다.
- 작업 현황의 기준과 상태는 총괄이 관리한다. 담당자는 작업 ID에 연결된 결과를 보고하며 공용 현황 파일을 동시에 임의 수정하지 않는다.
- 문서 링크는 관리 위치를 나타낸다. 링크된 문서나 기능이 아직 작성·구현되지 않았다면 존재하거나 완료된 것으로 취급하지 않는다.

## 5. 공통 작업 ID와 배정

작업 ID의 표기와 실제 목록은 작업 현황에서 관리한다. 작업은 `TASK-0001`, 변경 요청은 `CHANGE-0001`, QA 이슈는 `QA-0001` 형식으로 번호를 부여한다. 변경 요청과 QA 이슈에는 관련 작업 ID를 연결하여 배정부터 종료까지 추적한다. 번호 발급은 총괄이 관리하며 실제로 등록된 항목만 참조한다.

작업을 배정할 때 다음 항목을 명시한다.

| 항목 | 기록 내용 |
| --- | --- |
| 목표 | 이번 작업이 달성할 동작과 범위 |
| 담당 | 책임 역할과 배정된 에이전트 |
| 수정 범위 | 담당 파일·폴더, 공용 파일의 편집 책임자 |
| 기준 | 관련 명세·공통 계약의 위치와 버전 |
| 완료 조건 | 기대 결과, 검증 방법, 통합 조건 |
| 의존·미정 | 선행 작업, 승인 대기, 담당자가 결정하면 안 되는 사항 |

구체적인 계약이 아직 없으면 `구체 계약 미정`으로 표시하고, 계약과 관계없는 작업은 `이번 작업 해당 없음`으로 표시한다. 존재하지 않는 계약 버전이나 승인 기록을 만들어 배정하지 않는다.

## 6. 상태 흐름

### 작업

`제안 → 준비 완료 → 진행 → 구현 검토 → QA → 통합 → 완료`

- 준비 완료: 목표·담당·기준 계약·완료 조건이 정해져 착수 가능한 상태다.
- 구현 검토: 담당자가 자체 검증 결과와 함께 완료를 보고한 상태다.
- QA: 합의된 기대 결과와 실패 조건을 독립 검증한다.
- 통합: 관련 영역을 연결하고 실제 실행과 회귀 영향을 확인한다.
- 완료: 총괄이 결과와 검증 근거를 확인하고 종료한다.
- 어느 단계에서든 막히면 사유와 해제 조건을 적어 보류한다. 검토·QA 실패는 수정 작업으로 되돌린다.

### 계약·기획 변경 요청

`제안 → 영향 검토 → 승인·보류·반려 → 기준 문서 갱신 → 관련 작업 배정 → 구현·검증 → 종료`

- 요청에는 현재 기준, 변경 이유와 대안, 영향받는 영역, 검증 방법을 기록한다.
- 함수의 인자·반환뿐 아니라 동작 의미, 오류 처리, 상태 변경, 공용 데이터와 저장 스키마도 계약 변경에 포함한다.
- 구현자는 총괄 승인 없이 계약을 바꾸거나 다른 영역의 호출부를 일괄 수정하지 않는다.
- 총괄의 승인, 갱신된 계약 버전, 관련 담당에게 변경 기준 전달이 끝나기 전에는 기존 계약을 유지한다.
- 사용자의 판단이 필요한 변경은 사용자 결정 후 총괄이 작업을 배정한다.
- 승인 후에는 계약·구현·문서·테스트가 같은 기준을 따르도록 변경 범위를 함께 관리한다.

### QA 이슈

`발견 → 분류 → 담당 배정 → 수정 → 재검증 → 종료`

- 발견 시 재현 절차, 기대·실제 결과, 환경·대상 버전, 관련 작업 ID를 기록한다.
- 총괄이 구현 오류, 명세 불명확, 계약 문제를 구분하고 담당을 배정한다. 필요하면 기획 검토나 별도 변경 요청으로 연결한다.
- QA는 실패한 구현에 맞추어 기대 결과를 임의로 바꾸지 않는다.
- 수정 담당자의 자체 확인과 QA 재검증을 구분하여 남긴다. 재현되지 않거나 실행할 수 없었던 항목은 검증 완료로 표시하지 않는다.

## 7. 완료 보고

담당자는 작업 ID와 함께 변경 내용, 계약 변경 여부와 승인 근거, 수정 파일, 수행한 검증과 결과, 미검증 항목·남은 문제를 보고한다. 관련 명세·계약·QA 결과와 커밋이 있으면 링크한다.

총괄은 보고를 수집하여 작업 현황을 갱신하고 QA·통합 결과를 확인한 뒤 사용자에게 최종 결과를 전달한다. 담당자의 구현 완료 보고만으로 전체 작업 완료를 선언하지 않는다.
