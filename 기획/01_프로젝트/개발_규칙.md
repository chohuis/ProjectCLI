# 개발 규칙

상태: 사용자와 합의한 개발 방향을 운영 기준으로 기록. 코드 및 자동 검사 설정은 미구현.

역할·승인·작업 배정은 [운영 체계](운영_체계.md), 기술적 책임은 [코드 구조](../03_기술_설계/코드_구조.md)를 따른다.

## 개발 방법

- 영역 간 요청·응답·오류·상태 변경 계약을 먼저 합의하는 계약 중심 개발을 적용한다.
- 가벼운 도메인 설계를 사용한다. 같은 개념은 같은 용어로 표현하고, 개념의 의미는 기획 명세로 정한다. 실제 필요가 확인되지 않은 복잡한 패턴과 계층을 추가하지 않는다.
- 엔진, 표현, 저장의 책임을 분리한다. 구체적인 프로젝트·폴더·타입 이름은 착수 시 계약과 함께 확정한다.
- 핵심 계산, 계약, 암호화·저장·복구는 기대 동작을 먼저 정하고 테스트로 보호한다. 모든 내부 함수에 테스트를 기계적으로 추가하지 않는다.
- 시나리오는 상황 → 행동 → 결과로 표현하여 기획·구현·QA의 해석을 맞춘다. 별도 BDD 프레임워크는 현재 도입하지 않는다.
- CLI는 완성된 게임이 목표다. 작업 분할과 단계별 검증을 최종 구현 범위 축소로 해석하지 않는다.

## 코드 작성

- C# 관례를 따른다. 타입·메서드·속성은 `PascalCase`, 매개변수·지역 변수는 `camelCase`, 비공개 인스턴스 필드는 `_camelCase`를 사용한다.
- 코드 식별자는 영어, 설명 주석과 프로젝트 문서는 한국어를 기본으로 한다. 사용자 표시 문자열은 코드 식별자와 분리한다.
- 같은 개념에 여러 이름을 사용하지 않는다. 새 공용 용어는 기획·총괄과 맞춘다.
- 서식은 `.editorconfig`, 검사는 컴파일러·분석기로 자동화한다. 구체적인 설정은 프로젝트 구성 단계에서 적용한다.
- nullable 참조 형식을 활성화한다. 값이 없을 수 있는 조건을 명시하고, 경고 억제에는 이유를 기록한다.
- 사용자 요청의 정상적인 거부와 예외적인 실행 오류를 구분한다. 실패를 성공처럼 반환하거나 예외를 무시하지 않는다.
- 입력 해석, 규칙 계산, 파일 저장을 한 메서드에 혼합하지 않는다.
- 실제 중복과 사용처가 확인될 때 공통화한다. 새 의존성·패키지는 총괄 승인과 버전 고정 후 추가한다.
- 계약을 유지하는 담당 영역 내부 구현·리팩터링은 담당자가 진행할 수 있다. 공용 계약·다른 영역의 수정은 승인 절차를 따른다.

## 주석과 문서

| 위치 | 기록 기준 |
| --- | --- |
| 코드 내부 주석 | 처리 이유, 제약, 순서의 근거 등 코드만으로 알기 어려운 내용 |
| 공용 API XML 주석 | 의미, 인자, 반환, 실패 조건, 상태·시간 변경 등 계약상 중요한 동작 |
| 현재 설계 문서 | 현재 구조·사용법·확정된 동작 |
| 결정 기록 | 중요한 선택의 배경·대안·이유·영향·재검토 조건 |
| 작업 보고 | 변경 내용·계약 변경 여부·수행 검증·남은 문제 |

- 코드 내용을 그대로 반복하는 주석과 사소한 내부 함수의 형식적인 주석은 생략한다.
- 공용 계약의 선언과 동작 명세를 서로 연결하고, 변경 시 함께 갱신한다.
- 중요한 로직·파일 형식이 변경되면 관련 주석과 현재 명세를 같은 변경에서 수정한다.
- 평문 콘텐츠 전체, 복호화 키, 민감한 상태를 로그·문서·보고에 출력하지 않는다.
- 암호화 `.dat` 변경은 파일 차이만으로 검토하지 않는다. 관리 도구가 항목 ID·변경 필드·검증 결과를 요약하도록 하며, 공개할 값의 범위는 도구 설계 시 확정한다.

## 테스트와 QA

- 담당 구현자는 필요한 자체 테스트를 수행하고 QA는 명세 적합성·기능 연결·회귀를 독립 검증한다.
- 테스트는 외부에서 관찰 가능한 동작과 실패 조건을 중심으로 작성한다. 내부 구현을 그대로 복제하는 테스트와 일률적인 커버리지 목표는 두지 않는다.
- 재현이 필요한 시뮬레이션에는 시간·난수를 통제할 수 있는 구조를 적용한다.
- 실패를 숨기기 위해 테스트 기대값을 변경하지 않는다. 기대 동작 변경은 명세부터 검토한다.
- 실행한 명령, 결과, 미실행 항목과 원인을 구분한다. 검증 통과 후 의미 없는 반복 검증은 하지 않는다.
- 문서만 바뀐 작업은 링크·내용·Git diff를 확인한다. 실행 코드가 없는데 빌드·테스트를 통과했다고 보고하지 않는다.

## Git과 통합

- 하나의 목적을 가진 변경 단위로 커밋한다. 메시지는 `docs:`, `feat:`, `fix:`, `refactor:`, `test:`, `chore:` 접두사와 구체적인 목적을 사용한다.
- 총괄이 관련 파일을 명시해 스테이징하고, 의도하지 않은 변경과 비밀 정보가 없는지 확인한다.
- 하위 에이전트의 구현 완료와 전체 통합 완료를 구분한다. 총괄이 필요한 QA·통합 결과를 확인한다.
- 병렬 수정은 담당 파일을 분리하고 필요 시 별도 작업 폴더·브랜치를 사용한다. 같은 공용 파일을 동시에 수정하지 않는다.
- 커밋과 push는 사용자 요청 범위에서 총괄이 수행한다.
